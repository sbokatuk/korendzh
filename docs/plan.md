# План загрузки

Документ описывает учёт **планируемого рабочего времени** и сравнение с фактическими отработанными часами (`TimeEntry`).

Связано с [data-model.md](./data-model.md), [user-stories.md](./user-stories.md), [roles-permissions.md](./roles-permissions.md).

## Зачем нужен план

`TimeEntry` фиксирует **факт** — что воркер уже сделал. Чтобы понимать, насколько команда укладывается в ожидаемый объём (норма часов, графики 5/2 / 2/2 / 6/1), вводится **план**. Тогда менеджер на странице «План vs Факт» видит две линии — план и факт — и сразу понимает, есть ли отставание или переработка.

## Модель

### Таблица `PlanEntries`

Одна строка = «у пользователя `WorkerId` в день `WorkDate` запланировано `PlannedHours` часов».

| Поле | Тип | Описание |
|---|---|---|
| `Id` | GUID | Идентификатор |
| `WorkerId` | FK → User | Чей это план (воркер или менеджер) |
| `WorkDate` | date | На какую дату |
| `PlannedHours` | decimal(5,2) | Запланировано часов (0 = выходной, удаляется записью с `0`) |
| `CreatedById`, `CreatedAt`, `UpdatedById`, `UpdatedAt` | стандартные audit-поля |

Уникальный индекс по `(WorkerId, WorkDate)`. Если в этот день у воркера выходной — записи просто нет (или есть с 0, что эквивалентно отсутствию).

## Шаблоны графиков для bulk-fill

Bulk-fill применяет шаблон к диапазону дат, проставляя одинаковое количество часов в каждый рабочий день шаблона.

| Шаблон | Поведение |
|---|---|
| **5/2 (Пн–Пт)** | Рабочие — Пн, Вт, Ср, Чт, Пт. Сб/Вс — выходные |
| **6/1 (Пн–Сб)** | Рабочие — Пн, Вт, Ср, Чт, Пт, Сб. Вс — выходной |
| **2/2 сменный** | Скользящий цикл от даты старта: 2 дня работы, 2 выходных, 2 работы, 2 выходных, ... |
| **Каждый день** | Все дни в диапазоне — рабочие |

Параметры формы:
- Воркер(ы) — multi-select.
- Период `from`–`to`.
- Шаблон.
- Часов в день (по умолчанию 8, диапазон 0.25–24, шаг 0.25).
- Чекбокс «Заменить существующие записи» (по умолчанию true) — если включён, перед применением все записи плана выбранных воркеров в этом диапазоне удаляются; если выключен — рабочие дни шаблона перекрывают совпадающие даты, остальные старые записи остаются.

## Страницы

- `/Plan/Index` — мой план. Месячный список дней с инлайн-полями «Часы». Внизу — кнопка «Сохранить» (POST батчем сразу за весь месяц).
- `/Plan/Index?workerId={id}` — план другого пользователя (видно менеджеру/админу с проверкой через `DivisionScope`).
- `/Plan/Workers` — список воркеров для менеджера/админа со ссылкой на план каждого.
- `/Plan/Bulk` — форма автозаполнения по шаблону.

## Статистика

- `/Statistics/Plan` — линейный график Chart.js с двумя сериями (план и факт).
- Фильтры: период, **гранулярность оси X**, подразделение (только админу), воркер.
- Сводная таблица под графиком: total планового, total фактического, % выполнения, разница.

### Гранулярность графика (`PlanGranularity`)

Селектор «единица деления оси X» — для длинных периодов даёт читаемый график:

| Значение | Бакет | Лейбл на оси |
|---|---|---|
| Day | один день | `30 мар` |
| Month | календарный месяц | `Март 2026` |
| ThreeMonths | скользящие 3 месяца от даты `from` | `Мар 26–Май 26` |
| Quarter | календарный квартал | `Q1 2026` |
| HalfYear | полугодие H1 (Янв–Июн) / H2 (Июл–Дек) | `H1 2026` |
| Year | календарный год | `2026` |

Сначала сервис отдаёт **суточные** данные (`PlanVsActualDay` за каждый день диапазона), затем page-model группирует их через `PlanGranularityExtensions.GroupByGranularity(days, granularity, anchor: From)`. Это держит сервис простым и позволяет добавлять новые гранулярности без правок в SQL/EF.

Логика агрегации (`PlanService.GetPlanVsActualAsync`):
- Если выбран воркер — данные только по нему.
- Иначе если выбрано подразделение — суммирование по всем воркерам этого подразделения.
- Иначе — суммирование по всем пользователям системы (доступно только админу).

Для каждого дня в диапазоне `[from, to]`:
- `PlannedHours` = сумма `PlanEntry.PlannedHours` по выбранным воркерам.
- `ActualHours` = сумма `TimeEntry.Hours` по выбранным воркерам (без учёта soft-deleted благодаря глобальному фильтру).

## Миграция

После добавления модели в коде сгенерируйте миграцию (см. [migrations.md](./migrations.md)):

```
dotnet ef migrations add AddPlanEntries --project src/Korendzh.Infrastructure --startup-project src/Korendzh.Web
git add src/Korendzh.Infrastructure/Migrations
git commit -m "Add Plan: schedule + plan vs actual"
git push
```

На деплое `MigrateAsync` создаст таблицу `PlanEntries` и индексы — данные не теряются.
