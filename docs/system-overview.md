# Обзор системы

## Назначение

АрВи-транс (кодовое имя проекта — `korendzh`) — это **двухслойный сайт СТО**:

1. **Публичный лендинг** для клиентов: hero, выполняемые работы с фото и ценой, отзывы, контакты, редактируемые из админки текстовые страницы. Цель — клиенты понимают, что СТО умеет, и видят, как с ним связаться. Подробнее — [cms.md](./cms.md).
2. **Внутренняя система учёта рабочего времени** для сотрудников СТО — за логином. Воркеры отправляют отчёты о выполненной работе, менеджеры ведут учёт по подразделению, администраторы управляют менеджерами и одновременно наполняют публичный лендинг через CMS-админку.

С точки зрения посетителя: `https://бокатюк.бел/` показывает лендинг СТО; кнопка «Войти» в правом углу шапки ведёт сотрудника в его рабочий кабинет.

## Состав системы

Система состоит из трёх компонентов:

1. **Веб-приложение** — для админов и менеджеров (полный функционал управления и аналитики), а также для воркеров (ввод часов).
2. **Мобильное приложение** — кросс-платформенное на **.NET MAUI** (iOS + Android), в первую очередь для воркеров (быстрый ввод часов с поля). Только онлайн.
3. **Backend (REST API + БД + очередь уведомлений)** — общий для веб и мобильного клиента; см. [requirements.md](./requirements.md) для технологического стека.

## Роли пользователей

Подробная матрица прав — в [roles-permissions.md](./roles-permissions.md).

- **Worker (Воркер)** — отправляет отчёты о рабочих часах, может добавить новый автомобиль в общий справочник.
- **Manager (Менеджер)** — управляет своим подразделением (division): добавляет/редактирует воркеров, редактирует и добавляет их часы, добавляет автомобили, видит статистику по своему подразделению.
- **Admin (Администратор)** — управляет менеджерами, видит и редактирует отчёты по всем подразделениям, видит визуализированную статистику по всей организации.

## Подразделения (Divisions)

- Каждый менеджер владеет одним подразделением.
- Каждый воркер принадлежит одному подразделению (через своего менеджера).
- Админ видит данные всех подразделений сразу.

## Аутентификация и провижининг аккаунтов

- Email + пароль (стандартный флоу с восстановлением пароля).
- Вход через Google (OAuth 2.0).
- Сессии работают одинаково для веб и мобильного клиента (общий API, JWT или cookie-сессии).

### Создание аккаунтов

- **Первый админ** создаётся сидингом БД при деплое (см. [data-model.md](./data-model.md), раздел «Сидинг при деплое»).
- **Дополнительные админы** добавляются существующим админом через email-инвайт.
- **Менеджеры** — добавляются админом через email-инвайт.
- **Воркеры** — добавляются менеджером своего подразделения через email-инвайт.
- Открытой саморегистрации нет: попасть в систему можно только по приглашению.

### Восстановление пароля

- Self-service: пользователь запрашивает ссылку на email и сбрасывает пароль сам.
- Принудительный сброс: менеджер может инициировать сброс для своего воркера, админ — для любого пользователя. Письмо со ссылкой получает сам пользователь.

## Уведомления

Подробности — в [notifications.md](./notifications.md). Кратко:

- Email — для приглашений, сброса пароля и уведомлений об изменениях записей.
- Push (мобильное) — дублирует email-уведомления об изменениях записей; всё, что критично, всегда есть и в email.

## Основные сценарии

### Воркер отправляет рабочие часы

Воркер открывает форму ввода (веб или мобильное) и заполняет:

- **Дата** — день, в который выполнялась работа (выбор в календаре).
- **Часы** — количество отработанных часов.
- **Название задачи** — что делал.
- **Автомобиль** — текстовое поле с автокомплитом из справочника.
- **Государственный номер** — license plate.
- **Краткое описание** — свободный текст.

После отправки запись сохраняется в БД и привязывается к текущему воркеру.

Если воркер вводит автомобиль, которого нет в автокомплите, новая запись добавляется в общий справочник автомобилей и становится доступной для всех.

### Менеджер ведёт учёт по подразделению

Менеджер может:

- Добавлять и редактировать воркеров своего подразделения.
- Добавлять автомобили в справочник.
- Просматривать все отчёты воркеров своего подразделения.
- Редактировать любые поля любой записи воркера (часы, дату, задачу, автомобиль, описание).
- Добавлять записи от имени воркера (например, если воркер забыл).
- Видеть статистику по подразделению (см. ниже).

### Админ управляет организацией

Админ может:

- Добавлять и редактировать менеджеров.
- Видеть и редактировать отчёты воркеров любого подразделения.
- Видеть визуализированную статистику по всем подразделениям и менеджерам.
- Делать всё, что может менеджер, но в масштабе всей организации.

## Статистика и отчётность

Менеджеры (по своему подразделению) и админы (по всей организации) видят:

- **Часы по воркеру** — с разбивкой день / неделя / месяц.
- **Часы по задаче / проекту** — суммарное время по названию задачи.
- **Часы по автомобилю** — суммарное время, привязанное к каждому ТС.
- **Экспорт в Excel / CSV** — выгрузка любого из перечисленных срезов.

Для админов статистика дополнительно визуализируется (графики, диаграммы) для сравнения подразделений между собой.

## Жизненный цикл сущностей

- **User** — soft-delete через `IsActive`. Деактивированный воркер не может логиниться, но его исторические `TimeEntry` остаются у менеджера и в статистике.
- **Division** — может быть архивировано (`IsArchived`). В архивное подразделение нельзя добавить запись, но история и отчёты доступны.
- **Worker → другой Manager.** Админ может перепривязать воркера к другому подразделению. Старые записи воркера остаются «у воркера», новый менеджер их видит — это нужно для непрерывности отчётности.
- **TimeEntry** — soft-delete (`IsDeleted`); запись скрывается из списков, но остаётся в audit log и может быть восстановлена.
- **Car** — soft-delete через `IsActive`; убирается из автокомплита, не ломая исторические записи.

## Безопасность

- Все проверки прав — на сервере. Клиент рендерит UI на основании роли, но на каждый запрос бэкенд независимо проверяет права (см. [user-stories.md](./user-stories.md), US-S7).
- Пароли хранятся только хэшем (bcrypt / Argon2).
- Токены инвайта и сброса пароля хранятся только хэшем; оригинал виден один раз в email.
- Rate limiting на login и password-reset эндпоинтах.
- Все datetime в БД — UTC.
- Optimistic concurrency для редактирования `TimeEntry` (см. [validation.md](./validation.md)).

## Не входит в первую версию

Здесь будем фиксировать осознанно отложенный функционал по мере его всплытия:

- Workflow подтверждения часов менеджером (решено: не нужен).
- Offline-режим мобильного приложения (решено: не нужен).
- Мультиязычность UI (только русский).
- Мерж дублей в справочнике автомобилей (плановый административный инструмент).

## Что реализовано в коде

Backend (`src/Korendzh.Web` + `Korendzh.Infrastructure` + `Korendzh.Domain`):
- TimeEntry CRUD, soft-delete, optimistic concurrency
- Инвайт-флоу для воркеров и менеджеров, self-service сброс пароля
- ASP.NET Identity (Admin/Manager/Worker) + Google OAuth + JWT bearer для мобильного
- Audit log через SaveChangesInterceptor, очередь email-уведомлений с ретраями
- Статистика по воркерам/задачам/авто, CSV и xlsx экспорт, графики (Chart.js)
- Фоновая чистка просроченных токенов (`TokenCleanupService`)
- REST API для мобильного — см. [api.md](./api.md)

Мобильное приложение (`src/Korendzh.Mobile`) — скелет на .NET MAUI с LoginPage / EntriesPage / CreateEntryPage. См. [mobile.md](./mobile.md).

Тесты (`tests/Korendzh.Tests`) — юнит-тесты на TokenHasher, CarService, NotificationDispatcher, токены.
